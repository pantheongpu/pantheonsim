# Hopper features in turbo mode: design (design only, nothing built or run)

Base: turbo-fit cd30dd20. Tags: [D] documented (NVIDIA doc or the repo's own cited rule), [M] measured (by someone, in a named brief), [C] read from the code at the file:line given, [I] inferred, [U] unknown. No Hopper or Blackwell host was available; every statement about what a Hopper card does is [D], [I] or [U], never [M].

## 0. Summary

Turbo mode today sends no Hopper-feature kernel to a card: the sm_90+ mnemonics are class Never (include/vgpu/host_gpu.hpp:285-290 [C]) and any cluster or cooperative launch is refused (src/runtime/host_gpu.cpp:850 [C]). That is correct while the only cards measured are sm_86 and sm_89 (review-693 M2: the shim's CUtensorMap is not the hardware descriptor).

When the host card is itself an sm_90 part and the simulated profile is H100/H200 (so the image the card runs is the same sm_90/sm_90a cubin the simulator runs [C: host_gpu_source.hpp:42-44, 78-90]), the Hopper instructions need no translation: the card executes them natively. Exactly one thing in a Hopper kernel is simulator-private and must be rewritten at launch: the 128-byte tensor map. Three launch-API facts must change (cluster dimension, cooperative, shared-memory opt-in is already done). Everything else (wgmma, setmaxnreg, elect.sync, mbarrier tx, cp.async.bulk non-tensor, DSMEM) is native card work gated only by evidence.

Work items, smallest first: W1 class-table gate by host_sm (no data translation), W2 tensor-map translation, W3 cluster/cooperative launch through cuLaunchKernelEx with occupancy pre-check, W4 (optional, later) maps living in global memory. W2 and the logic of W1/W3 are CI-testable without a Hopper card; "the card accepts it and computes the same" is not.

## 1. What is simulator-private

### 1.1 The tensor map (the only private data format)
* The shim's cuTensorMapEncodeTiled/Im2col write the simulator's own 128-byte layout: include/vgpu/exec/tensormap.hpp:27-140 (encode at :103, decode at :146 [C]). Fields: global address at 0x00; rank, type, interleave, swizzle, NaN fill at 0x08; strides at 0x0c+4i (16-byte units) and 0x1c; extents-1 at 0x20+4i; element strides and box0 at 0x34; box1..4 at 0x38; im2col word at 0x70; magic "GPUTMAP1" (kMagic, :28) at 0x78 [C]. The header says the tile fields sit where NVIDIA's descriptor has them, "probed with ptxas" [C, claim of the file]; whether the whole object is bit-identical to the driver's output is [U], and the magic at 0x78 means it is not byte-identical (the 0x78 slot is the simulator's own [C: header comment]). NVIDIA documents the object as opaque, "only through CUDA APIs and PTX" [D: cuda.h CUtensorMap, header comment :1-3]. So the only supported way to a real map is the card driver's own cuTensorMapEncodeTiled/Im2col.
* The shim validates the documented encode rules and then drops one argument: `l2Promotion` is range-checked (:268) but not stored anywhere in the layout [C]. A translation therefore must pick the l2Promotion itself (a cache hint, performance only [D: cuTensorMapEncodeTiled, "l2Promotion" argument]; CUTLASS uses L2_128B [I]). Optional additive fix: store the original value in a spare byte (0x3c-0x6f is unused by encode [C]); exact-mode decode ignores it.
* Rejected by the shim so they never reach translation: interleave != NONE, swizzle 128B_ATOM_32B_FLIP_8B (:~280-285 [C]); the Wide im2col variants are not exported by the shim at all (driver_api.cpp:7489-7490 and runtime_api.cpp:8089-8091 list only Tiled, ReplaceAddress, Im2col [C]).
* The simulator's decode fails on foreign bytes (interpreter.cpp:13578-13591 [C]); the same magic check is the translation's recogniser.

### 1.2 How a kernel receives a tensor map
* As a kernel parameter: a `__grid_constant__ CUtensorMap` (128 bytes, 64-byte aligned), or a struct holding several of them (CUTLASS 3.x `Params` carry their TMA descriptors this way [I: from CUTLASS source layout, not read in this repo]). The simulator reads it with read_tensor_map at the generic address of the parameter (interpreter.cpp:13578 comment: "a kernel parameter (__grid_constant__), global memory or constant memory" [C]).
* The launch hands the host path `args` as one byte vector per declared parameter (host_gpu.cpp:841, :1909-1911 [C]); ParamDecl carries size and align (ast.hpp:1489-1500 [C]); cuLaunchKernel is given `params.data()` pointing at copies of these vectors, so an edit of the copy never touches simulator state [C: `keep`, :1909].
* In global or constant memory: written by cudaMemcpy/cudaMemcpyToSymbol of an encoded map, or by device-side `tensormap.replace` (which "compiles to plain stores", tensormap.hpp:76 [C]). These bytes are inside the mirrored window, so the card would read simulator bytes. Not translatable from the args alone (W4).
* The global address inside a map is a window address, identical on the card because the card was given the simulator's address window (cuMemAddressReserve at the simulator's base, host_gpu.cpp:582 [C]). The existing word scan of arguments for host-mapped pointers (:861-866 [C]) already sees the map's first qword (the address) as a pointer.

### 1.3 Launch attributes
* Cluster: LaunchConfig.cluster (launch.hpp:133 [C]) is set from cuLaunchKernelEx's CU_LAUNCH_ATTRIBUTE_CLUSTER_DIMENSION (driver_api.cpp:3363-3406 [C]; attribute id 4, entries 72 bytes, asserted at :3366 [C]) or from the kernel's compiled `.reqnctapercluster` (fn.req_cluster [C]). Both are refused at host_gpu.cpp:850 [C]. The card path calls only cuLaunchKernel (function pointer table at :86, call at :1913 [C]); it has no cuLaunchKernelEx symbol.
* Cooperative: same refusal (:850). Needs cuLaunchKernelEx with CU_LAUNCH_ATTRIBUTE_COOPERATIVE (id 2, :3367 [C]) or cuLaunchCooperativeKernel [D].
* Dynamic shared memory above 48 KB: already handled. fits_card checks the opt-in limit (cuDeviceGetAttribute 97 = MAX_SHARED_MEMORY_PER_BLOCK_OPTIN [C: stub_driver.c:34]) and cuFuncSetAttribute(MAX_DYNAMIC_SHARED_SIZE_BYTES) is called at :1857 and :1907 [C]. NVIDIA: opt-in is required above 48 KB [D, CUDA C++ Programming Guide, "Shared memory"]; the H100 limit is 227 KB per block [D, Compute Capabilities table, cc 9.0]. Nothing to build; the rental should confirm it on cc 9.0 [U on the card].
* Hardware-visible-through-the-API only: cluster launch on a part without clusters is CUDA_ERROR_INVALID_CLUSTER_SIZE (912) [M on an RTX 3060 per driver_api.cpp:418, :3405 comments [C]]; on Hopper the launch can also fail for a shape that cannot be co-scheduled, which cuOccupancyMaxActiveClusters answers beforehand [D].

### 1.4 What is NOT private (runs natively, no translation)
wgmma/HGMMA, setmaxnreg/USETMAXREG, elect.sync/ELECT, mbarrier expect_tx/complete_tx/try_wait (SYNCS), non-tensor cp.async.bulk (UBLKCP), stmatrix/STSM, distributed shared memory loads/stores and cluster barriers (UCGABAR), griddepcontrol. They operate on card registers, card shared memory and card barriers; their operands are addresses in the kernel's own shared window or the identity-mapped global window [I]. They are class Never only for lack of card evidence (host_gpu.hpp:283-284 comment [C]). One unlisted gap: UTMACCTL (prefetch/invalidate a descriptor, decode.cpp:2928-2931 [C]) is not in the Never list, so it would be admitted as Unlisted; it takes a descriptor address and belongs with the TMA group.

## 2. Launch-time translation algorithm (W2, plus W1/W3 hooks)

Where: Impl::launch, after fits_card and ensure_mapped, before the first cuMemcpyHtoD push (host_gpu.cpp:~1857-1860 [C]). Rationale: encoding is a host-side function that writes only the caller's buffer [D: cuTensorMapEncodeTiled writes `tensorMap`; "needs no context" is the shim author's comment, driver_api.cpp:3887-3890 [C], [I] for the real driver], so a failure there leaves card state untouched and the launch can go to the simulator without `dead=true` (all later failure paths set dead, :1913 onward [C]).

```
translate_tensor_maps(args, card_encoder) -> {ok, patched_args | refusal}
  for each arg a (the per-parameter byte vector, a copy):
    for off in 0, 64, 128 ... while off + 128 <= a.size():     # maps are 64-byte aligned inside a 64-aligned parameter [D: 64-byte alignment rule, encode_tiled :264]
      if load64(a+off+0x78) != kMagic: continue
      TensorMap m; if !m.decode(a+off): refuse(Corrupt)         # magic but unreadable fields
      call = tiled or im2col from m.im2col
      map dataType from m.type via the CUtensorMapDataType enum (TmapType numbering IS that enum, tensormap.hpp:21-23 [C])
      globalStrides = m.stride[1..rank-1]  (rank-1 entries, bytes; stride[0] is the element size and is NOT passed [D])
      boxDim = m.box[0..rank-1]; elementStrides = m.elem_stride[0..rank-1] (a stored 0 was decoded as 8 [C])
      interleave NONE (shim refuses others); swizzle = m.swizzle (enum identical to CUtensorMapSwizzle [C]); oobFill = m.oob_nan
      l2Promotion = stored value if W2b else L2_128B (hint) [I]
      im2col: lowerCorner/upperCorner = m.lower/upper[0..rank-3]; channelsPerPixel = m.channels; pixelsPerColumn = m.pixels
      cached = cache[128 sim bytes]  (encode is a pure function of its arguments [I]; cache cannot go stale because the key is the map bytes)
      r = card_encoder(buffer64, args...)     # the CARD's cuTensorMapEncode*, resolved by dlsym from the same libcuda (host_gpu.cpp:100-105 style) 
      if r != SUCCESS: refuse(CardEncode, r)
      overwrite a[off..off+128) with buffer64
  return patched args
```
Properties and limits:
* Recognises maps by magic, not by type: the kernel's parameter list carries no CUtensorMap type in the ParamDecl [C: ast.hpp ParamDecl has no such flag], and CUTLASS embeds maps in structs. A false positive needs 8 bytes equal to "GPUTMAP1" at 0x78 of a 64-aligned block; [I] negligible, and the copy is only used for this launch.
* Real maps pass through untouched (no magic). A program that already holds a real map cannot exist: the shim made every map [C].
* An unaligned or mid-parameter map (not 64-aligned relative to the parameter start) is not found; the kernel would then run on the card with a simulator map. Guard: also scan every 8-byte offset for the magic when the parameter is >= 128 bytes and refuse (not translate) if a hit is not 64-aligned. [I; cheap]
* The address must be backed on the card first (ensure_mapped(hi) with hi covering the map's address range [C: :1838-1844]); the existing args word scan reaches the base, but a map's extent (dim and strides) can exceed the bytes the existing range logic derives from `ranges` [U: ranges computation not re-read for this note]. W2 must add the map's byte extent (address .. address + sum over dims of (dim-1)*stride + elem) to the ranges the push covers, otherwise the card would read an unpushed hole. This is the most likely silent-wrong-data bug and the first thing the unit test should pin.
* Fallback ladder, all before any card state change: (1) magic found but decode fails or card encode returns an error: refuse this launch (FitRefusal::TensorMap, new), kernel runs in the simulator, mode stays on; (2) driver exports missing cuTensorMapEncode*: the symbol is optional like cuFuncGetAttribute (:106 [C]); tensor-map kernels stay in the simulator; (3) three consecutive refusals of one kernel: remember per kernel (the verdict cache, :878 [C]). Never reaches dead=true.
* Verified mode: VGPU_HOST_GPU_VERIFY compares card and simulator outputs after the launch (note_simulated, :1583-1600 [C]); the rental uses it as the oracle. Turbo is not bit-accurate by owner decision, so acceptance (section 5) is a tolerance, not equality, except for data-movement kernels.
* Kernels whose maps live in global memory or are rewritten in-kernel (W4): see 2.1.

### 2.1 Maps outside the parameters (W4, optional, default off)
Cases: Triton 3.x TMA descriptors in a device buffer, CUTLASS ptr-array grouped GEMM that `tensormap.replace`s, cuBLASLt internals [I for all three]. They are indistinguishable from data by mnemonic. Options: (a) refuse any kernel whose SASS has a UTMA* instruction whose descriptor address does not come from the parameter bank (needs a provenance scan over the kernel's uniform-register dataflow; the SASS scanner's classifier has no such provenance today [C: it classes by mnemonic only, host_gpu.hpp:298-340]); (b) translate in place on the card: scan the pushed chunks for the magic, encode, write the card copy, and restore the simulator's bytes into the card copy after the launch so pull-back does not return translated bytes into simulated memory (the pull-back logic assumes card chunks equal what the kernel wrote [I]). (a) first: conservative, no new state, and only keeps these kernels in the simulator. (b) only after a card run shows (a) is losing a measurable share (census, section 4).

### 2.2 Cluster and cooperative (W3)
* Add optional `cuLaunchKernelEx`, `cuOccupancyMaxActiveClusters`, `cuOccupancyMaxActiveBlocksPerMultiprocessor` to the table. Missing symbols: the gate keeps refusing line 850's cases.
* Cluster launch: when cfg.cluster != 0 or fn.req_cluster != 0, the card must report cc >= 9 [D: clusters need cc 9.0] (attribute 75 [C]); build a CUlaunchConfig with the cluster attribute (same 72-byte layout the shim already asserts, :3366 [C]); for a cluster of more than 8 CTAs, cuFuncSetAttribute CU_FUNC_ATTRIBUTE_NON_PORTABLE_CLUSTER_SIZE_ALLOWED first [D] (the shim tracks it as non_portable, :2949 [C]); pre-check cuOccupancyMaxActiveClusters > 0 for this config and dynamic shared size [D], else refuse (a failing launch would set dead). Grid must be a multiple of the cluster shape [D].
* Compile-time cluster kernels (`__cluster_dims__`/`.reqnctapercluster`) launch with plain cuLaunchKernel on the card [D]; the pre-check still applies.
* Cooperative: same pattern with the cooperative attribute and a co-residency pre-check (active blocks per SM x SM count >= grid). Independent of Hopper; folds in for free.
* The simulator's own cluster limits (profile GPC layout, cluster.hpp:35 [C]) are irrelevant on the card.

## 3. What is testable in CI without a Hopper card, and what needs one

Without a card (framework-free, hosted CI; test file name suggested tests/unit/test_host_gpu_tmap.cpp, wired like test_host_gpu_logic [C: unit tests exist for the pure parts]):
1. Pure translation function with an injectable encoder callback (no libcuda). Cases: map as whole parameter; two maps inside a 300-byte struct at offsets 0 and 128 (others unchanged byte for byte); no magic leaves args identical; magic at a 32-aligned offset refuses; decode failure refuses; encoder error refuses and leaves the args untouched; cache hit does not re-call. Check recorded call arguments against the documented signature of cuTensorMapEncodeTiled: dataType numbering, globalStrides has rank-1 entries in bytes, boxDim and elementStrides rank entries, interleave NONE, swizzle enum, oobFill, l2Promotion, and for Im2col the corner arrays with length rank-2, channelsPerPixel, pixelsPerColumn [D: cuda.h].
2. Round-trip property: for randomised valid argument sets, encode_tiled/im2col (header-only inline, tensormap.hpp:257, :345 [C]) then translate must hand the callback exactly the original arguments except l2Promotion. Mutations to demonstrate failing: off-by-one rank-1 in strides; strides left in 16-byte units; swizzle or dataType mapping shifted; box taken as extent-1; elementStrides 0 not mapped back; im2col lower/upper swapped.
3. Range-coverage test: for a map whose extent exceeds the args-derived ranges, the computed push ranges include the full extent (mutation: use the base only).
4. Class-table gate: under host_sm == 90 and want_sm == 90 the Hopper mnemonics are admitted as a new class (or Unlisted), under host_sm 86/89/100/120 they stay Never; TMA mnemonics are admitted only when the translation succeeded; UTMACCTL joins the TMA group. Mutation: gate keyed on the profile instead of the card.
5. Stub-driver e2e (nvidia/tests/e2e/host_gpu_stub_driver.c, run_host_gpu_stub.sh, ctest e2e_host_gpu_stub [C: CMakeLists.txt:4333]): extend the stub with cuTensorMapEncodeTiled/Im2col that log their arguments to STUB_LOG, cuLaunchKernelEx and cuOccupancyMaxActiveClusters that log the attribute list, STUB_SM=90 (the stub already takes STUB_SM, :44-45 [C]). A simulated-H100 launch of a kernel with a cluster attribute and a tensor map then shows: encode logged with the documented arguments, cluster attribute 4 with the right dims logged, cuLaunchKernel/Ex called after, and with STUB_SM=86 the launch refused and nothing logged. Whether this e2e can run on hosted CI depends on how run_host_gpu_stub.sh produces its kernels (it builds .cu files [C: host_gpu_lazy.cu]); [U] whether hosted CI has nvcc; a PTX-text kernel through the shim's runtime API avoids that [I].

Needs a card (precisely):
* that the real driver accepts the translated map, and a TMA load through it delivers the right bytes (the stub cannot execute UTMA);
* the byte-level difference between the simulator's map and the driver's own output for the same arguments (a 128-byte diff table, minutes of work; decides whether a cheaper byte-patch could ever replace the encode call; do not build that without it) [U];
* cuLaunchKernelEx with a cluster attribute, cuOccupancyMaxActiveClusters, the non-portable attribute, error codes for impossible shapes and whether a failed pre-checked launch poisons the context [U];
* cooperative launch co-residency behaviour;
* wgmma/setmaxnreg/mbarrier-tx kernels computing within tolerance of the simulator (numerics: Hopper tensor-core accumulation vs the simulator's model [U]);
* performance (does the mode pay: kernel time vs the simulator) [U];
* shared-memory opt-in of 227 KB accepted [D, unverified here].

## 4. Share of real kernels affected

Census file /home/saqib/.cache/pantheonsim-briefs/round9-parallel/census.md did not exist when this was written; numbers below come from images.md (the cubin counts it measured) and public knowledge, all tagged. Counts are cubin kernels or images present, not launches.
* PyTorch 2.10+cu130 libtorch_cuda: 456 cubins each of sm_75, 80, 86, 90, 100, 120, plus 4 sm_90a and 60 each sm_100a/103a [M, images.md:65]. So of the sm_90-family images, 4 of 460 (0.9 %) are the arch-specific ones that can hold wgmma/TMA/setmaxnreg [C: `a` cubins run on exactly their arch]; the 456 plain sm_90 cubins are ordinary kernels (cluster launches and cp.async.bulk can still appear, count [U]). Most PyTorch eager work on an H100 profile is therefore not blocked by the TMA gap; it is blocked today only by the image choice (a Hopper card runs the sm_90 cubin natively).
* cuBLASLt (ollama mlx lib): sm_90 221 cubins vs sm_90a 1,376 [M, images.md:64], 86 % of its Hopper-family images are sm_90a (wgmma-class). Which of them use TMA descriptors is [U]; CUTLASS 3.x Hopper mainloops do [D: CUTLASS 3.x docs describe TMA + wgmma warp-specialised kernels] and the library's Hopper GEMMs are CUTLASS-derived [I].
* FlashAttention-3 is Hopper-only (sm_90a, wgmma + TMA) [I, public]; Triton on sm_90 emits wgmma, and TMA when the program uses tensor descriptors [I]; both build their maps host-side and pass them as parameters or through a device buffer (Triton's descriptor path, W4) [I].
* Plain-compile corpora (PolyBench, Rodinia, HeCBench, CUDA Samples, 656 binaries): 0 limited to sm_90+ images [M, images.md:71]; sm_90-only content appears only where the source asks for it (cuda::barrier, cp.async.bulk, clusters) [M, ptx-retarget.md:55]. So TMA affects the modern-ML-library slice (cuBLASLt/CUTLASS/FA3/Triton), not the classic corpus.
* Share of launches by work item [I, to be replaced by census]: W1 alone (no maps): kernels with wgmma/mbarrier-tx/elect/setmaxnreg but cp.async loads or UBLKCP, probably a minority; W2 unlocks CUTLASS-style param-borne maps, the majority of Hopper GEMM and attention launches in the libraries above; W4 covers the rest (Triton, grouped GEMM) and is the uncertain tail.
* Why the turbo mode wants them: these kernels are exactly the ones the simulator runs slowest (large wgmma GEMMs); the benefit is concentrated in few, long launches [I, consistent with section 16.1 of docs/perf-design/12-host-gpu-turbo.md: the big speed-ups were tensor-core GEMMs, 183 s to 3.8 s, M on A10G].

## 5. What a rental would test

* Instance: one sm_90 card with a recent driver (CUDA 13 era, driver >= 580 [I]). Cheapest candidates, check availability and price on the day [U for current price]: a single-H100 EC2 instance (p5.4xlarge, if offered in a region the account has quota in [I]); a single H100 on Vast or RunPod (marketplace; exclude the two known-impaired UUIDs ba0e84a6, b5410126 [memory]; at most 2 Vast cards at once); not Lambda (user stopped Lambda launches). H200/GH200 are also sm_90 [D]; GH200 is aarch64 and the driver path default is the x86_64 one (host_gpu.cpp:523 [C]), so avoid it for the first run. AWS launches need explicit approval (project rule); a 1-GPU on-demand H100 at roughly the low single digits of USD per hour is [I].
* Time: about 3 to 4 hours: 45 min to install the CUDA 13.0 toolkit and build the simulator on the box (the shim and one runtime build; no nvcc on server3 is why this must run on the card box); 30 min diff table and API probes (section 3, card list); 90 min kernels; 30 min repeat and copy-back. Rigs self-shut at 300 minutes.
* Kernels, in order: (1) a one-CTA cp.async.bulk.tensor 2-D copy (CUDA Samples or the repo's test_hopper PTX, tests/unit/test_hopper.cpp:908 [C]) with a map made by the shim; (2) the same with a 3-D and an im2col map; (3) a cluster launch with DSMEM exchange (tests/unit/test_hopper.cpp has cluster PTX [C]); (4) a wgmma GEMM (CUTLASS example 48-ish Hopper GEMM [I]); (5) a cuBLASLt bf16 GEMM through the simulator's own libraries if it routes to sm_90a kernels [U]; (6) PyTorch cu130 bf16 matmul and scaled_dot_product_attention on the h100 profile; (7) FA3 or Triton TMA if installable.
* Acceptance criteria: (a) with VGPU_HOST_GPU_VERIFY=all and turbo on, every kernel above runs on the card (stats.card_runs > 0, counted per kernel) and compares equal on data movement kernels (1,2,3 bit-equal) and within the existing tolerance on GEMMs (host_gpu_tol.hpp default [C]); (b) zero launches end in dead=true and zero Xid/err 700/719 in the log; (c) the pre-checks refuse an impossible cluster shape and the run continues; (d) the card diff table of section 3 is captured and committed (<100 KB, no host identifiers); (e) turbo end-to-end time for the GEMM and attention kernels is below the simulator's by a factor recorded per kernel (no target promised); (f) with the mode forced off (VGPU_HOST_GPU_FIT=0 and TURBO_OFF classes) behaviour is unchanged and exact mode's outputs/counters are bit-identical [project rule].

## 6. Blackwell

* Documented [D]: sm_100/sm_103/sm_120 exist; arch-specific cubins (sm_100a, sm_103a) run on exactly their architecture, family-specific (`f`) within the family [C: host_gpu_source.hpp:42-49 comment]; the tensor-map encode API is the same cuTensorMapEncodeTiled with extra data types and swizzle modes (16U6, 128B_ATOM_32B/64B) which the shim already models (tensormap.hpp:21-24 [C], cuda.h 12.8+ [D]); clusters are a Hopper-and-later feature [D]; tcgen05 and tensor memory are sm_100a features [D: PTX ISA 9.7.18], and the simulator has class entries for them (UTCMMA, LDTM, STTM, UTC* in the Never list [C: host_gpu.hpp:285-290]).
* Inferred [I]: the same translation (W2) and cluster plumbing (W3) would apply, because the descriptor and cluster interfaces are the same API; tcgen05/TMEM state lives on the card and needs no translation; the sm_100a image chosen on a B200 host is the simulator's own for a B200 profile. A Hopper card given a B200 profile cannot run sm_100 images, so the card-side image would be the sm_90 cubin, whose maps (if a map uses a Blackwell-only type or swizzle) the Hopper driver would refuse at encode, which the fallback ladder (section 2) turns into a simulator run [I].
* Unknown [U]: whether the Blackwell driver's descriptor is the Hopper one with additions; tcgen05 numerics vs the simulator; cluster sizes and occupancy on a real B200; whether sm_103/sm_120 behave as the simulator's profiles assume.
* Therefore nothing is to be claimed for Blackwell: no access, no measurement. Keep the gate keyed to host_sm == 90 only; Blackwell mnemonics stay Never until a Blackwell card run exists. Say in docs only that the design is expected to carry over [I].

## 7. Order of work when a Hopper card is available
W1+W3 gate and launch plumbing and W2 translation behind one switch (VGPU_HOST_GPU_HOPPER=1, default off until the acceptance run passes); unit tests 1-4 first (CI, no card), stub e2e (5), then one rental. W4 only if the census shows a large share of kernels stay out. The class gate must key on the card's sm (host_sm), never on the simulated profile (review-693 M2 was exactly a profile/card mix-up).
